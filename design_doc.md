## 1. Контекст проекта

### 1.1 Бизнес-задача

#### Проблема

Команда, сопровождающая агента на базе LLM, получает жалобы на неверные или неполные ответы. Чтобы найти причину, инженер изучает трейс, код той версии агента, которая дала ответ, и доступные логи. Сам плохой ответ не показывает, где возник сбой. Поиск мог не найти нужный материал, контекст мог не попасть в промпт, модель могла его не использовать, а инструмент мог вернуть ошибку.

После разбора инженер предлагает исправление. Его приходится отдельно проверять на исходном запросе и других примерах: изменение может помочь в одном случае и ухудшить работу агента в целом. Такой разбор занимает время, а без проверки одни и те же ошибки могут повторяться.

#### Почему без LLM-системы не справиться

Основой разбора служит таксономия сбоев, которую утверждает команда подключённого агента. Для каждого вида сбоя она описывает признаки в трейсе, логах и коде. Правила обнаруживают явные ошибки, например код ошибки инструмента. В остальных случаях нужно сопоставить жалобу с последовательностью действий агента и их результатами. Языковая модель помогает установить, где возникла проблема, и предложить изменение. Система запускает агента отдельно и проверяет изменение на исходном случае и контрольном наборе, когда есть критерий правильного результата.

Langfuse служит источником трейсов. Сервис сопоставляет их с доступными логами и кодом агента, чтобы подготовить проверяемый диагноз.

#### Почему именно это решение имеет смысл

Система даёт инженеру результат разбора в одном месте. Он видит вероятную причину, шаг сбоя, фрагменты трейса и кода, а также результат проверки изменения. Инженер решает, как исправить агента. Разобранные случаи сохраняются в контрольном наборе для проверки следующих изменений.

#### Критерии успеха с точки зрения бизнеса

Успех решения оценивается по двум показателям. На одном наборе жалоб инженер тратит меньше времени на правильное решение об исправлении, чем при разборе в Langfuse с кодовым ассистентом. За месяц экономия времени инженеров превышает стоимость запуска и поддержки системы.

Правильность диагноза и проверки исправления оценивается отдельно. Если вывод неверен, быстрое получение отчёта не считается успехом.

### 1.2 Пользователи и сценарии использования

Системой пользуется внутренняя команда из трёх до пяти инженеров, которая разрабатывает и поддерживает агента на базе LLM. Инженер отмечает проблемный ответ и создаёт заявку с `trace_id`. Комментарий необязателен.

Разбор выполняется в фоне. Сервис изучает трейс, доступные логи и код, запускает агента и пытается воспроизвести сбой. Затем он возвращает отчёт в Markdown с причиной, шагом сбоя, подтверждающими фрагментами и результатом проверки возможного исправления. Инженер получает готовый разбор для ревью.

Для расчёта нагрузки принимаем от трёх до пяти жалоб в день и не более двух одновременных разборов. Это проектное допущение, которое будет уточнено по фактическому потоку жалоб. Инженер не ждёт результат у экрана, поэтому важнее сократить время его участия в разборе.

Неверный диагноз может привести к плохому изменению агента. Поэтому отчёт отделяет подтверждённые причины от предположений и показывает, когда данных для вывода недостаточно.

### 1.3 Границы, ограничения и допущения

#### Функциональные границы

Прототип представляет собой сервис с открытым исходным кодом, который команда разворачивает у себя. При подключении проекта команда настраивает Langfuse, модель и виды сбоев. Затем сервис получает данные по идентификатору трейса, проводит разбор и формирует отчёт в Markdown. Подключение другого агента через настройки возможно, если в его трейсе видны нужные шаги.

Таксономия описывает виды сбоев и признаки, по которым их можно различить. Команда утверждает подходящие для своего агента виды. Сервис даёт начальный пример, проверяет настройки и использует принятую таксономию при разборе.

Вид сбоя определяем по первому неверному шагу. Для поиска проверяем, был ли нужный материал в источнике и пропал ли он в выдаче. Для промпта сравниваем результаты поиска и инструментов с тем, что получила модель. Ошибку ответа модели ставим, когда правильные данные были во входе, а ответ им противоречит. Ошибку инструмента подтверждаем его результатом или кодом ошибки. Если нужного сравнения нет, диагноз остаётся неподтверждённым.

Для анализа кода команда даёт доступ к репозиторию агента на чтение и связывает трейс с версией кода. При подключении она также задаёт способ запуска агента и тестов в отдельной среде. Сервис сам изучает нужную версию и проверяет предложенное изменение. Решение о его применении принимает инженер.

#### Границы прототипа

В прототипе мы строим таксономию для выбранного агента, включая четыре вида сбоев из темы курса. На другом наборе трейсов проверяем, можно ли сменить таксономию без доработки сервиса.

Трейсы берём из Langfuse. Сбор трейсов, дашборды, хранение логов и выпуск изменений в рабочую версию агента остаются за командой. Разбор инфраструктурных сбоев, задержки и стоимости работы агента в прототип не входит.

#### Допущения

В трейсе должны быть видны значимые шаги агента, их входы и результаты. Для анализа кода нужна версия репозитория, соответствующая вызову. Логи используются, если их можно связать с трейсом. Если по доступным данным нельзя установить, почему ответ плохой, сервис сообщает об этом в отчёте.

Пресет проверки запускает агента отдельно от рабочей версии и использует тестовые доступы к внешним сервисам. Для проверки результата нужны примеры с известным правильным поведением. В прототипе используются синтетические или обезличенные данные.

## 2. Контракт сервиса

### 2.1 Контракт

| Поле | Контракт | Как проверим |
|---|---|---|
| **Вход** | `trace_id` и необязательный комментарий. Для проекта настроены Langfuse, привязка трейса к версии кода в Git, таксономия и команда запуска агента. | Проверяем конфигурацию, доступность трейса и версии кода до начала разбора. |
| **Выход** | Сначала возвращается `analysis_id` и статус задачи. По завершении доступен `report.md`. В нём указаны диагноз, шаг сбоя, ссылки на наблюдения в трейсе и код, результат воспроизведения и проверки изменения. Тест и diff прикладываются, если их удалось подготовить. | Проверяем структуру отчёта и ссылки. Сравниваем диагноз с размеченной причиной. |
| **Поведение при неуверенности** | Статус `confirmed` означает, что сбой на конкретном шаге подтверждён сравнением с правильным прогоном или тестом. Статус `probable` означает, что признаки есть, но проверки недостаточно. Статус `unresolved` означает, что данных не хватило. Возможную причину в коде отчёт описывает отдельно от наблюдаемого сбоя. | Проверяем статусы на случаях с известной причиной и на неполных трейсах. |
| **Чего не обещаем** | Патч для каждого сбоя, доказанное исправление без критерия правильности, выпуск изменений в рабочую версию агента. | Проверка отчётов, где воспроизведение или проверка исправления не удались. |
| **Нефункциональные** | Разбор идёт в фоне. Артефакты хранятся в развёртывании команды. Модель вызывается у выбранного ею провайдера. Время и стоимость разбора ограничиваются бюджетами раздела 3. | Проверяем жизненный цикл задачи и хранение артефактов. Измеряем время и стоимость. |

Исправление считается проверенным, если тест падает на исходной ревизии, проходит после изменения, а контрольный набор не ухудшается.

**Контракт одной фразой:**

> По `trace_id` сервис разбирает сбой на конкретной версии агента, пытается воспроизвести его и возвращает отчёт с доказательствами, результатом проверки и предложением исправления. Неподтверждённые выводы помечаются отдельно.

### 2.2 Сценарии взаимодействия

**Основные сценарии**

| Сценарий | Вход | Что делает сервис | Результат |
|---|---|---|---|
| Причина подтверждена | `trace_id` | Сопоставляет трейс с кодом, воспроизводит сбой, готовит тест и проверяет изменение. | Отчёт со статусом `confirmed`, доказательствами и результатами запусков. |
| Причин несколько | `trace_id` | Проверяет каждую гипотезу на трейсе и повторном запуске. | Отчёт с основной причиной и оставшимися гипотезами. |
| Исправление не прошло проверку | `trace_id` | Сохраняет результаты запуска исходной версии и кандидата. | Отчёт с диагнозом и объяснением, почему изменение не принято. |

**Исключительные сценарии**

| Ситуация | Поведение сервиса | Результат |
|---|---|---|
| Трейс недоступен или не содержит нужных шагов | Останавливает задачу до диагностики. | Статус ошибки с причиной. |
| Не удалось связать трейс с версией кода | Разбирает доступный трейс и фиксирует пробел в данных. | Отчёт без выводов о коде. |
| Агент не запустился или превысил лимит времени | Сохраняет ошибку запуска и доступные наблюдения. | Отчёт без заявления об успешном воспроизведении. |
| Нет критерия правильного результата | Проверяет наблюдаемые признаки сбоя, но не объявляет исправление доказанным. | Диагноз со статусом `probable` или `unresolved`. |
| Провайдер модели недоступен или вернул неверный формат | Повторяет вызов в пределах бюджета задачи. | При повторной ошибке задача завершается с причиной. |

### 2.3 Диалоговая логика и тон

Одной заявке соответствует один разбор. Диалога с инженером и истории сообщений нет. Состояние задачи хранит выбранные фрагменты трейса и кода, гипотезы и результаты запусков. Между заявками сохраняются настройки проекта и проверочные случаи. В контекст модели попадают только данные, нужные для текущего шага. Отчёт пишется на русском языке, кратко и со ссылками на доказательства.

## 3. Три бюджета и SLO

### 3.1 Качество

Первый порог проверяем на 20 случаях с заранее внесёнными сбоями, по пять случаев каждого вида. Он служит ориентиром для прототипа, а не оценкой качества на реальных жалобах.

| Метрика | Как считаем | Цель | Порог отката |
|---|---|---|---|
| Верный вид и шаг сбоя | Оба совпали с разметкой. | Не менее 16 из 20 случаев. | Меньше 14 из 20. |
| Ложный уверенный диагноз | Статус `confirmed` при неверной причине. | Не более 1 из 20. | Более 1 из 20. |
| Доказательства в отчёте | Ссылки ведут к фрагментам, которые подтверждают вывод. | Не менее 19 из 20 отчётов. | Меньше 18 из 20. |
| Проверенное исправление | Тест падает на исходном коде, проходит на новом, контрольные случаи не ухудшаются. | 100 % отчётов с пометкой о проверенном исправлении. | Любое ложное подтверждение. |

### 3.2 Задержка

Разбор идёт в фоне. Его длительность зависит от размера трейса и времени запуска агента.

| Этап | Что измеряем | Бюджет |
|---|---|---|
| Приём заявки | Время до выдачи `analysis_id`. | P95 до 2 секунд. |
| Полный разбор | Время по размеру трейса и числу запусков агента. | Цель определим после первых прогонов. |

При пяти жалобах в день и двух параллельных задачах средний разбор должен занимать меньше 9,6 часа, иначе очередь будет расти.

### 3.3 Стоимость

При нагрузке от трёх до пяти жалоб в день получаем от 90 до 150 разборов в месяц. Для расчёта берём 100 тысяч входных и 10 тысяч выходных токенов на один разбор. Фактический расход зависит от трейса и числа запусков.

| Модель OpenRouter | Цена за миллион токенов, вход / выход | Один разбор | Месяц |
|---|---|---|---|
| GPT 6 Sol | 2 / 10 долларов | 0,30 доллара | От 27 до 45 долларов |
| Claude Sonnet 5.5 | 2 / 10 долларов | 0,30 доллара | От 27 до 45 долларов |
| GLM 5.3 | 0,89 / 2,80 доллара | Около 0,12 доллара | От 11 до 18 долларов |

Альтернатива сервису: инженер разбирает каждую жалобу вручную в Langfuse и с кодовым ассистентом. При условном одном часе на жалобу это от 90 до 150 часов в месяц. Фактическое время ручного разбора измерим на тех же случаях, на которых проверим сервис.

### 3.4 Компромисс

Качество диагноза важнее времени разбора. При исчерпании бюджета задача завершается отчётом с уже проверенными фактами и непроверенными гипотезами.

### 3.5 SLI и SLO

| SLI | Как считаем | SLO | Допустимый сбой |
|---|---|---|---|
| Готовность отчёта | Готовые отчёты среди заявок с доступным трейсом и настроенным запуском. | Не менее 95 %. | До 5 заявок из 100. |
| Приём заявки | Время до выдачи `analysis_id`. | P95 до 2 секунд. | До 5 медленных заявок из 100. |
| Формат отчёта | Наличие диагноза, статуса, доказательств и результата проверки. | 100 %. | Нет. |
| Ошибочный статус `confirmed` | Проверка на случаях с известной причиной. | Не более 1 случая из 20. | 1 случай из 20. |

Время полного разбора измеряем по размеру трейса и числу запусков агента.

## 4. Архитектура решения

### 4.1 Схема по семи блокам

Схема слева направо: клиент → шлюз → оркестратор → движок инференса → хранилища / инструменты → обратно; наблюдаемость под всем. Вставьте картинку или ASCII-схему.

```
[клиент] → [шлюз] → [оркестратор] → [инференс]
                         ↕
                  [хранилища] [инструменты]
        ────────── наблюдаемость ──────────
```

Для каждого блока: что делает у нас, что берём готовым, что пишем сами и почему. Правило курса: руками пишется только то, чего нет в готовом виде, или что специфично для наших данных.

| Блок | Что делает в нашей системе | Берём готовое | Пишем сами и почему |
|---|---|---|---|
| Клиент | [ ] | [ ] | [ ] |
| Шлюз | [аутентификация, лимиты, роутинг, ретраи, учёт токенов] | [LiteLLM / OpenRouter / шлюз провайдера / …] | [ ] |
| Оркестратор | [сборка промпта, вызов инструментов, агентный цикл, guardrails] | [LangGraph / PydanticAI / Agents SDK / …] | [ ] |
| Движок инференса | [API провайдера или self-host] | [провайдер / vLLM / SGLang / llama.cpp] | [ ] |
| Хранилища | [документы, индекс, память диалога, кэш, состояние агента] | [Postgres + pgvector / Qdrant / Redis / …] | [ ] |
| Инструменты | [поиск, код, внешние API, БД] | [MCP-серверы, коннекторы] | [ ] |
| Наблюдаемость | [логи, трейсы, метрики, eval в проде, фидбек] | [Langfuse / Phoenix / LangSmith + Prometheus / Loki / Sentry] | [ ] |
